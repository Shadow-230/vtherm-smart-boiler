# Review of VTherm Smart Boiler 0.2.1 — 2026-09-26

A read-only analysis of the plugin at commit `0f101ee` (branch `main`): requirements, compliance
with the specification, the logic itself (including errors in the specification), Home Assistant,
Versatile Thermostat, architecture, async behaviour, robustness, code quality, security, tests,
compatibility, documentation and CI. Nothing in the code or the specification was changed.

## 1. Scope, inputs and method

**Inputs.** Specification: `SCOPE.md`, `PLAN.md`, `docs/plan-0.1.md`, `docs/plan-0.2.md`, `docs/plan-0.2.1.md`
(with CLAUDE.md "Verified facts" and `research/*.md` as facts). Code: `custom_components/vtherm_smart_boiler/` —
54 Python files (~12,700 lines: 29 pure `core/` modules, `transport/`, the HA layer), manifest, icons, EN/PL
translations. Tests: `tests/` (~13,600 lines: core, integration, sim, tools, release). Also `sim/`, `tools/`,
`scripts/`, `devenv/`, `.github/workflows/`, `pyproject.toml`, `hacs.json`. VT 10.4.0 and SmartPI 0.4.0 in
`vendor/` and `vtherm_api` 0.5.0 / HA 2026.9.3 in `.venv` were read only for interface facts.

**Not read, by the user's instruction or the project's rules:** the session summary, the earlier review reports
(`docs/review-2026-09-24.md`, `research/2026-09-24-code-review/`), `home-assessment.md` (private), `devenv/local.env`
and `devenv/ssh/`. Consequently, the absence of installation-specific data was checked by searching for hard-coded
entity IDs, not against the author's installation. No Home Assistant instance was contacted. Network sources (HA
developer docs and blog, hassfest sources, hacs.xyz, VT's repository) were read online on 2026-09-26; nothing from
the network was stored.

**Method.** Six requirement tasks (SCOPE §1–§6, SCOPE §7–§12, PLAN + plan-0.1 + plan-0.2, plan-0.2.1, VT and
vtherm_api, HA + HACS) each built a requirement list and then a requirement → code → test matrix, reading the code
and the tests behind every row. Nineteen review tasks read the whole code in partitions (control core, monitor
core, control loop, transport, lifecycle, VT integration, config flow, entities and diagnostics, tooling and CI)
and across it (control state machine, VT model and priorities, async, security and robustness, the specification
as a document, four test reviews including coverage). Every finding and every proposed missing test went to an
adversarial verifier told to refute it, with two independent verifiers for anything rated critical; findings
refuted went to Appendix F. Duplicates across tasks were merged by hand: the 377 verified findings (and 9 refuted ones) became the 190
problems of section 3. Short Python snippets confirmed several findings; no file of the project was changed.

**Tools** (Appendix A): the whole suite with line and branch coverage, mypy strict, ruff check and format, and ruff
with every rule for information. pylint is not installed and was not installed. hassfest and the HACS action run
only as GitHub actions and were not run.

**Severity.** Critical: a realistic risk of a cold house without an alarm, a boiler left under the plugin's control,
a write to the boiler's persistent memory, cycling caused by the plugin, overheating a circuit, or a control loop
stopping without a safe state. High: wrong control or monitoring in a realistic case, a double loop or leaked
listeners, a wrong state after restart or reload, a blocked release, a safety-relevant contradiction in the
specification. Medium: an edge case, an untested important path, a quality problem with a real regression risk, an
applicable IQS Bronze/Silver rule not met. Low: style, small inconsistencies, documentation.

## 2. Summary and overall assessment

The plugin is a careful, safety-minded piece of work. The control and monitoring laws are pure functions in
`core/` with no Home Assistant import (enforced by a test), the HA layer is thin, every write goes through guards
with read-back, every exit hands the boiler back and an owed hand-back is stored, retried and shown. The
engineering hygiene is high: 911 tests pass, line and branch coverage is 96.75 %, mypy strict and ruff are clean,
real VT 10.4.0 thermostats run in-process, and the specification records its decisions and open items openly.

No critical problem survived verification. Five are high:

- **P-01** a corrupt store is read as a new installation: the "controlling" marker and an owed hand-back are lost,
  and the monitoring period restarts (stand-alone: a week without heating, without an alarm);
- **P-02** the control switch becomes unavailable — and cannot be switched off — whenever the monitor's refresh
  fails, while control keeps writing;
- **P-03** the same entity can be both heating switch and hand-back switch, which toggles it every minute for ever;
- **S-01** the specification's own OTGW rule ("off" = CH=0) leaves an on/off thermostat masked after an HA crash,
  contradicting its promise that the thermostat takes over;
- **S-02** the lower water bound is not tied to the boiler's minimum power, so mild weather can bring the short
  cycling the project was started to fix.

58 problems are medium and 127 low (111 in code, 17 in tests, 62 in the specification in total). The themes: the
control state is not durable enough on the unhappy paths (corrupt or unread store, failed setup, delayed saves);
availability and logging are coupled to the monitor; configuration validation misses a few dangerous
combinations (same switch twice, steps above 1 K, zones without the data a criterion needs, zero zones); the
guards' memory and the link-loss logic reset too easily; and the specification leaves several priorities undefined
(no zone known, frost protection behind valves VT closed, outside change with reaction "information", the comfort
correction against principle 13, VT's activation delay).

Of 843 requirements, 545 are covered by an implementation and a test checking it, 123 partially, 22 are
implemented without a test, 37 are not implemented (all but one belong to the open 🔒 release steps K1, K5, R2,
K4–K7 — README, licence, repository, brand), 9 contradict the code or HA, 16 cannot be decided from the repository,
91 are out of scope for 0.2.1 or not applicable. Release readiness: the code is close; publication is not
(hassfest and the HACS action cannot pass before K1, K5 and R2), and the test HA (J2, J4) is still to come.

Overall: code **8/10**, tests **8/10**, specification **7/10** (thorough, but with the contradictions and gaps of
section 4), readiness for a real boiler **not yet** — fix the high items and decide S-01, S-02, S-03, S-05 and S-11
first.

## Appendix B. Control and hand-back state machine

Reconstructed from `core/controller.py`, `core/loop.py`, `control.py`, `coordinator.py`, `__init__.py`,
`transport/writers.py`: 16 states, 31 transitions, 24 judged correct.

States: monitor only (no unit); entry in SETUP_ERROR/RETRY with a debt in the store; hand-back-only unit; waiting
for the switch to restore (≤ 60 s); DISABLED; NOT_ALLOWED (blockers); controlling (HEATING / IDLE / FROST /
FALLBACK); WAITING_DATA; HANDED_BACK after stale data (resumes on its own); HANDED_BACK latched by an alarm (off →
on); writes stopped (guard blocked); internal error; holding (the boiler may hold a plugin value); hand-back owed
(retried every minute, stored); hand-back failed shown (alarm + fixable issue); unit stopped.

Transitions judged wrong or undefined:

| From → to | Trigger | Why | Problem |
|---|---|---|---|
| WAITING_DATA (not controlling) → WAITING_DATA forever | link lost after a restart, after a blocker, or when switching on | no `boiler_link_lost` alarm; a restart clears the earlier alarm | P-08 |
| writes stopped (reaction "information") → controlling | reload or restart | the block is not stored; the spec defines no exit | S-11 |
| internal error → cleared | HA restart (switch restore) | known C10 | Open after R6 #6 |
| start with a debt → no unit (SETUP_RETRY) | first monitor refresh fails | no hand-back, no issue | P-05 |
| start → store overwritten with defaults | exception in `link.async_detect()` before the store is read | the controlling marker is lost | P-04 |
| IDLE or start → HEATING (ZONES_UNKNOWN) | every zone unknown (VT reload, zones not ready) | as specified, but without a grace period | S-03 |
| owed / WAITING_DATA / decision interval → waits longer | wall clock set back | known C9 | Open after R6 #8 |

States where control can get stuck: a lost link without active control (no alarm; stand-alone = no heat); a
value hand-back the device does not show on the setpoint entity (retried every minute for ever, exit only by the
repair flow or a new session); SETUP_RETRY with a debt (no retry, no issue); unparsable `taken_with` (issue only,
untested); a latch restored while the switch was not restored; writes stopped with reaction "information" until
the session ends (silently resumed by a reload); a SmartPI pause lost in the first 120 s after a crash (learning
off for good); `monitoring_period` after an unreadable store (7 days, stand-alone without heat, no alarm).
